## 2026-09-16 · K15 — `engineering-perf-optimization-process`: step 0 (ownership) and a second case study — the ladder climbed for constraints, not throughput (52 skills)
**Decision:** Add `references/case-study-two-tier-cache.md` and fold its lessons into the skill: a **step 0 — who else writes this data, and how many instances serve it** — in `escalation-ladder.md` and in Gate 2, with a table of which cache contracts are honest per writer situation (sole writer → invalidation in the write path; unseen second writer → TTL-only with a stated window; interleaved writers on user-visible state → no cache; inputs to an irreversible write → never). Step 2's "invalidate on write" is now conditional on being the sole writer. Steps 3–4 gain the cross-instance rungs the ladder lacked: TTL clamp of the in-process copy to the shared entry's remaining lifetime, downward-only jitter, a serialisation check before a type enters a shared tier, a shorter negative TTL for caller-supplied keys, refresh-ahead behind a cross-instance lock (breakdown), and an epoch-prefixed clear that reaches every instance. Six anti-pattern rows, eval #7, one glossary term (`TTL-only contract`). No new skill; 52 stays.
**Why:** the existing ladder and its one case study climb for throughput — the trigger at every step is RPS or a profile. The origin repo's cache design (11 families, 15 pods, 30-minute content staleness, a legacy backend writing the same tables) was forced by ownership and instance count instead: it took the in-process step before the shared-store step, added the shared tier because 15 pods multiplied origin load rather than because of store latency, and needed four mechanisms the ladder never named to keep two tiers honest. Its list of what is *not* cached (grading inputs, interleaved learner state, per-user keys, rows mutated in place, the write path — served by a request-scoped memo instead) is as load-bearing as the list of families, and the skill had no place for it. A reviewer following the old text would have approved the one design the constraints forbid: write-through invalidation for data another system writes.
**Rejected:** a separate `caching-design` skill (the decisions are the ladder's decisions — splitting them would leave the ladder recommending the wrong order); porting the origin repo's Go seam as a reference implementation (the kit is stack-agnostic and de-branded; the mechanisms are described, the code is not shipped); making step 0 a numbered rung with a trigger RPS (ownership is a precondition of every cache step, not an escalation); renumbering the ladder to match the order this case took (the order is constraint-dependent — the fix is to say so, not to bake in a second fixed order).

## 2026-09-16 · K14 — `reality-gate`: two mechanisms the six could not see — engine parity and cost (52 skills)
**Decision:** Extend `reality-gate` from six to eight mechanisms without adding a skill. **7 — test engine is not the real engine:** integration containers pinned to a major tag (`mysql:8`) while the deployed server runs another version; fix is one constant owning the image plus an `engine-parity` script that prints both `VERSION()`s (AC-006). **8 — cost blindness at the seam:** the AC for a seam change states no cost number, so a correct-but-expensive change — a payload column carried through `ORDER BY`, one query per item, an unbounded page, one remote call per row — is green on every gate; fix is AC-007, one measured number per seam touched (queries, rows, bytes or calls per request) taken on real-sized data before and after, with a per-seam table in REFERENCE §8 and the MySQL payload case kept as the worked example, not the definition. Wired the same way as K13: table rows, REFERENCE sections, two AC blocks and reviewer lines in the template, two `audit.sh` heuristics, an eval, a SCENARIO behaviour, two glossary terms, and a sentence in `orchestrate`'s Packetize and Verify steps stating that the AC — not Verify — is where the question gets asked.
**Why:** on 2026-09-14 a history endpoint in the origin repo answered 500 (`Error 1038: Out of sort memory`) on the deployed MySQL 9.4 once a payload column grew past 300 KB, while the identical statement, payload and `sort_buffer_size` passed on the `mysql:8` (8.4) container the suite booted — at any payload size. Every K13 gate was green: the schema was the real dump, the container ran, the diff read correctly. None of the six mechanisms names either cause. Both were found by cross-team QA on dev, a day late. The same week a browser header added to a handler never reached the CORS allowlist: correct code, green tests, silent failure in the browser — the same shape (a question no gate asks), fixed in the repo by a source-scanning test rather than in the kit. Rule 3 of Workflow A already said a bug that maps to no mechanism earns a new row; this is that row, twice.
**Rejected:** raise `sort_buffer_size` (treats the symptom; the read still ships 350 KB to serve 30 bytes); a new `performance-gate` skill (the failure is the same family — a green suite that disagrees with reality — and a second skill would split the AC template that packets copy from); folding the cost question into `backend-go-database` (Go-only and advisory; the gate has to sit where ACs are written, stack-neutral, or an executor without database experience never meets it); making AC-007 a hard ratio threshold (some list paths legitimately serve what they read — the number is pasted and the reviewer reads it; only a wide ratio without a stated reason is rejected); naming #8 after the incident ("read budget", JSON column, `ORDER BY`) — one case is not a class, and a kit read by other teams needs the class: no cost number in the AC.

## 2026-09-10 · K13 — `reality-gate`: verify seam changes against something the agent did not write (52 skills)
**Decision:** Add `skills/engineering/reality-gate` (self-contained: SKILL, REFERENCE, `scripts/audit.sh --probe`, AC template, evals, SCENARIO). It names six mechanisms by which a coding-agent loop produces a green suite that fails on the real database, config, or client: silent integration skips, hand-written test schema plus invented fixtures, tautological fakes at the seam, a replay suite living outside the repo, untested wiring/config, and no client-contract evidence. One rule: a change touching a persistence/config/response-shape seam is not verified until observed against a real schema, a container that actually ran, a recorded real request, or a legacy diff — and the reviewer pastes that output. Wired as a gate, not prose: a checklist line in `tdd-go`, a sentence in `orchestrate`'s verify step, a dispatcher row, a workflow chain (#13), and three glossary terms.
**Why:** an origin repo followed `tdd-go` on every packet and reached 354 test files, yet QA against the dev database found many 500s and shape bugs. The rule that would have caught them ("one acceptance test per feature with real containers and real router") was already in `tdd-go` — in a table and a paragraph, not in the checklist or any acceptance command. An agent optimizes for the AC it is handed; an un-gated rule does not exist for it. The audit script found all six mechanisms there (60 silent skips, 13 SQL-text assertions, 101 config keys vs 14 in `.env.example`, zero goldens, replay scripts named in reports but absent from git).
**Rejected:** enforce stricter test-first in the loop (costs tokens, and the agent still writes fake and code together — the failure is at the seam, not in ordering); fold the content into `tdd-go` (Go-only and process-only; this rule is stack-neutral and belongs in review/AC, where non-Go stacks and orchestrators read it); fold into `quality-gates` (canonical upstream body — kept close to upstream by K2/K5; a pointer row is added instead); a `.jimmy/` output-only skill with no script (the counts are what make the audit reproducible across repos).

## 2026-09-09 · K12 — Correct four product skills against their primary sources; extend two canonical bodies
**Decision:** Audit of seven `skills/product/` skills against transcripts of the source lecture series (the five lecture-derived skills were committed 2026-09-02, five days *before* those guides were rewritten from raw transcript — so they inherited a generation of AI-fabricated detail). Findings applied: `subscription-paywall` §2 loses the invented "mid-tier selection can roughly double" multiplier and the "more than three = paralysis" law (kept as a shape to test), gains the trial-vs-reverse-trial signup gate (card vs email) and "retention is the core, not the model"; `growth-loops` stops crediting the smile curve as the PMF signal (flattening is; a smile is a cycle you have not designed for) — frontmatter included; `product-strategy` drops unsourceable EVT/DVT sample sizes and gains two sections (owning the technology as vendor-negotiating position; expert VoC vs customer VoC arriving too late); `product-vision` drops an unsourced "10% of features". `go-to-market` verified claim-by-claim and left unchanged — its Rogers percentages are externally correct even though the source speaker never said them. Two canonical sage-product bodies extended additively, not re-voiced: `opportunity-map` gains the four-position read (underserved / table stakes / overserved / appropriately served), a **Reduce candidates** parallel output with template row, and an explicit `max(gap,0)` ≠ `abs(gap)` guard; `jtbd` gains the **Confirm** stage (aligning `SKILL.md` with its own methodology reference, plus templates and examples), the start-at-Execute heuristic, the job-map-is-not-a-user-journey test (SKILL, quality checklist, and a new `pitfalls.md` entry), consumption-chain jobs, a Value Proposition Canvas run order, and the B2B performer/buyer/blocker split. Outcome-count ranges in `jtbd` (50–150 / 15–30) were checked and **left alone**.
**Why:** the kit's own anti-fabrication rule applies to the kit. A claim that entered a skill through a fabricating intermediate is not automatically wrong — three of the four flagged skills matched their transcripts closely, and real third-party frameworks (Hook model, center-stage effect, Rogers' diffusion curve) stay — but an unsourced *number* presented as an effect size is a defect, because readers act on multiples. The two canonical additions are corrections toward upstream rather than local invention: `Confirm` is in Ulwick's Universal Job Map and was already in this skill's own reference file, and the overserved quadrant is half of the model the skill implements — without it the skill can only ever add work, never fund it by cutting. The `abs(gap)` guard was earned: a real company shipped that substitution, which inverts the ranking and points investment at exactly what should be cut.
**Verified 2026-09-09 (same day):** `opportunity-map` was accepted by a real run rather than a new SCENARIO file (upstream has none): scoring a product beta produced the four-position read, a three-item reduce list, and — re-scored with `abs(gap)` as a control — confirmed the guard, since all three reduce candidates jumped from 2–3 to 7 and the reduce list vanished. That run also exposed a gap now fixed: importance and satisfaction often rest on different evidence (measured build vs unvalidated assumption), so they are tagged per dimension and the ordering is marked provisional. Follow-up on `okr-outcome-architect`: added the missing upstream handoff (`jtbd` → `opportunity-map`), §3b converting a desired-outcome statement into a KR by attaching baseline/target/date, and the rule that a Committed KR must name the customer-outcome position it serves — a KR aimed at a table-stakes or overserved need scores 100% and changes nothing; dropped an unattributed "#1 mistake in the handbook" appeal.
**Rejected:** delete the flagged frameworks outright (they are published third-party methods; the defect was the invented magnitude, not the concept); rewrite the five lecture skills from the corrected guides wholesale (most content verified; a rewrite would churn reviewed text and re-risk drift); add a fourth `Reduce` decision beside pursue/monitor/defer in `opportunity-map` (changes the canonical decision set — a parallel output preserves it); "fix" `jtbd`'s outcome ranges to match one lecture (a second lecture by the same speaker gave 50–150, matching the skill — the lecture that said 150–250 was the speaker misremembering); create `SCENARIO.md` for `jtbd`/`opportunity-map` (upstream has none; deferred pending owner call — the four non-canonical skills' scenarios were updated).

## 2026-09-02 · K11 — Preserve the engineering philosophy as a shared, stack-neutral contract

## 2026-09-02 · K10 — Dose workflows by risk; reduce complexity before isolating it
**Decision:** Make Tier 1/2/3 dosage consistent across the README, usage guide, operating workflow, eager dispatcher, and routing appendix. `product-council` is required only for Tier 3, explicit red-team/pitch requests, or consequential product/platform decisions. Extend the existing design kernel with one progressive-disclosure complexity reference: classify essential/accidental complexity; scan shared mutable state, side effects, dependencies, control flow, and code size; then choose `reduce`, `isolate`, or `accept`. Functional Core / Imperative Shell remains a heuristic. In TypeScript backends, design messages/roles/contracts before classes and use OOP to isolate necessary state, lifecycle, coordination, DI boundaries, and adapters; `tdd-go` remains Go-only.
**Why:** the prior public surfaces contradicted the dosage rule by requiring council for every build, and the design vocabulary named testability techniques without explaining when FP removes moving parts versus OOP encapsulates unavoidable ones. Source review also showed that FP makes data flow and dependencies explicit but does not erase essential complexity or necessarily reduce code size.
**Rejected:** mandatory full chains (bureaucracy); separate OOP/FP/React/TypeScript skills (routing noise and framework sprawl); "functional everything" (distorts effectful/lifecycle work); "everything is an object" (adds mutable graphs and indirection); renaming or generalizing `tdd-go` in v0.1.x (unnecessary compatibility break).
